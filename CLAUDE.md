@AGENTS.md

## Commands

- `npm install` — dependencies (lockfile is `package-lock.json`).
- `npm run dev` — dev server on http://localhost:3000.
- `npm run build` / `npm run start` — production build and serve.
- `npm run lint` — ESLint flat config (`eslint.config.mjs`: `eslint-config-next` core-web-vitals + TypeScript).
- Type-check: `npx tsc --noEmit` (no `typecheck` script exists).
- There is no test runner configured, so there is no test or single-test command.

Environment: copy `.env.example` to `.env.local`. `NEXT_PUBLIC_API_URL` defaults to `http://localhost:8000/api/v1` when unset. The backend is not in this repo; every auth call assumes it is running at that URL. Google Maps settings (`NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`, `…_MAP_ID`, default center/zoom, service-area bounds) are read only in `lib/maps-config.ts`; without a key the maps must degrade to a notice. `NEXT_PUBLIC_*` values are inlined at build time, so changing `.env.local` needs a rebuild.

## Architecture

**Stack:** Next.js 16 App Router, React 19, Tailwind CSS v4 (via `@tailwindcss/postcss`), framer-motion, lucide-react. The `lang` is `es` and all user-facing copy is in Spanish; keep new UI strings in Spanish.

**Route groups** (`app/`):
- `(auth)/` — `login` (hosts both login and register; `AuthView` toggles between `LoginForm` and `RegisterForm`), `register` (just redirects to `/login`), `complete-profile`, `google-callback`, and `restaurant/register`.
- `(site)/` — the public site and the regular user's area: `page.tsx` (landing), `explore` (directory), `establishments/[id]` (detail), `details` (redirect for `?id=`), `profile` (user profile), `favorites`, `plans` and `notifications`. Its `layout.tsx` renders the single shared `Navbar`, whose links change by role (visitor / user / restaurant / admin).
- `(restaurant)/` — the restaurant panel. Its `layout.tsx` checks role and `APPROVED` status; `PENDING`/`REJECTED` accounts only see `/restaurant/status`.
- `(admin)/` — the admin console. Its `layout.tsx` checks the `admin` role.
- **Navigation shells:** the public site uses `components/common/Navbar.tsx` (from `md` up: logo, search → `/explore?search=`, links, bell, avatar menu) plus `PublicBottomBar` on phones, both mounted in `app/(site)/layout.tsx`. Admin and restaurant layouts have a sidebar (from `md`), an `AreaTopBar` (breadcrumb, bell, user menu) and a `BottomTabBar` on phones; `/restaurant/status` renders without any shell. The avatar menu (`UserMenu`) holds the role link and logout. `components/layout/Footer.tsx` is mounted once in `app/layout.tsx` for every page.
- **Placeholder destinations:** sections that exist in the designs but not in the app (Nosotros, Contacto, Soporte, Configuración) use `components/ui/PlaceholderLink.tsx`, an `href="#"` link that does not navigate. Search for `PlaceholderLink` to find them when removing or implementing one. Items with no `href` in `NAV_ITEMS`/`TAB_ITEMS` render as placeholders.
- **Notifications:** `components/notifications/NotificationsProvider.tsx` (inside `AuthProvider` in the root layout) polls `/notifications/unread-count` every 60 s while there is a session and the tab is visible, plus once on focus; `useNotifications()` → `{ unreadCount, latest, loadLatest, refresh, markRead, markAllRead, remove }`. `components/common/NotificationsBell.tsx` (in `Navbar`, `AreaTopBar` and `/restaurant/status`) shows the badge and the last 5; `/notifications` is the full inbox. Notification `link`s are internal routes; open them through `safeNotificationLink`.
- **Maps:** `components/map/` holds the Google Maps pieces (`@vis.gl/react-google-maps`, AdvancedMarker with a Map ID, Places API (New) autocomplete). Import the heavy ones (`EstablishmentsMap`, `StaticLocationMap`, `LocationPickerMap`) from `components/map/lazy.tsx` (`next/dynamic`, `ssr: false`); `MapsProvider` mounts `APIProvider` per view and falls back to `MapUnavailable` without a key or on load/auth failure. `LocationPicker.tsx` (+ `LocationPicker.ts`: `validateLocation`, `locationPayload`, `locationFromProfile`) is used by restaurant registration, profile and re-application; the backend requires coordinates at registration. `/explore` keeps every filter in the URL and does not remount on changes (that would recreate the map).
- **Reviews:** `lib/reviews-api.ts` (B3 contract, `MODERATION_CATEGORY_LABEL`, `reviewErrorMessage`) and `components/reviews/`. The detail page renders `ReviewsSection` (summary, action by `viewer_can_review`/`viewer_review_block`, own review, form, paginated list; `?review=1` opens the form). The public detail no longer has `reviews`: it has `recent_reviews`, `rating_distribution`, `category_rank` and `viewer_*`. A blocked comment arrives as `comment: null` + `moderation_notice` and must render `BlockedContentNotice`; only the author's `MyReview` carries the original text. Review photos upload to the `reviews` folder (`POST /reviews/upload-url`).
- **Restaurant reviews and schedules (F4):** `/restaurant/reviews` (summary, tabs Sin responder/Todas/Respondidas, `ReplyEditor` passed to `ReviewCard` through `replySlot`) and `/restaurant/schedules` (`components/establishment-management/SchedulesEditor.tsx`, which takes `load`/`save` so the admin can reuse it; its rules in `schedules.ts` mirror the backend's `schedule_service`). API functions are in `lib/restaurant-api.ts`. After a reply changes, dispatch `RESTAURANT_REVIEWS_CHANGED` so the panel menu's unanswered counter reloads.
- **Admin console (F5):** `lib/admin-api.ts` (B5 contracts, `RESOLVE_ACTIONS_BY_TARGET`, `MODERATION_ACTION_LABEL`) and `components/admin/` (`ModerationReviewCard`, `ModerationActionModal`, `ConfirmWithReasonModal`, `ReportCard`, `NotifyUserModal`, `ModerationHelp`). Pages: dashboard, establishments (list filter in the URL, detail with suspend/reactivate and map, `[id]/manage`), users, reviews (`?queue=flagged|reported|blocked|hidden`, `establishment_id`, `user_id`), reports, activity. Call `announceAdminCountsChanged()` after an action that changes the menu counters (pending requests, open reports). Approve/reject only from `PENDING`.
- **Plans (F6):** `lib/plans-api.ts` (B6 contract, `REMINDER_LABEL`, `PLAN_LIMITS`, `planErrorStep`/`invalidItemIds`, `planIcsUrl`, `planGoogleCalendarUrl`) and `components/plans/`. Pages under `app/(site)/plans/` (`layout.tsx` = `RequireRole` user + verified phone): `/plans` (calendar + upcoming), `/plans/new` (place search, or `?establishment=`), `/plans/[id]` (`?created=1`, `?updated=1&rescheduled=1` banners), `/plans/[id]/edit`. The wizard is `PlanBuilder.ts`/`.tsx` (import it as `PlanBuilder.tsx`); opening-hour slots come from `slots.ts`, which mirrors the backend's `is_open_at` (midnight-crossing segments). The `.ics` is a plain link to the API, never a Blob (iOS Safari needs a real navigation). The backend computes the total; the UI only estimates it.
- **Favorites and establishment type (F7):** `lib/favorites-api.ts` and `components/favorites/`. `FavoritesProvider` (root layout, inside `NotificationsProvider`) loads `GET /favorites/ids` once for a verified `user` and exposes `useFavorites()` → `{ mode, isReady, isFavorite(id, fallback), isPending, toggle }` with optimistic overrides and its own toast. `FavoriteButton` hides itself for restaurant/admin, sends visitors to login and unverified users to `/complete-profile`; it must never be inside an `<a>` (cards put it next to the link, see `components/establishments/EstablishmentCard.tsx`). `/favorites` requires `user` + verified phone. Types: `ESTABLISHMENT_TYPES`/`ESTABLISHMENT_TYPE_HINT`/`establishmentTypeLabel` in `lib/establishments-api.ts`, `EstablishmentTypePicker` in registration and `ProfileEditor` (send `establishment_type` only when it changed; the backend rejects `null`), `/explore?type=`.
- **Privacy (F8, Ley 1581):** `lib/legal.ts` (versions that must equal the backend's `PRIVACY_POLICY_VERSION`/`TERMS_VERSION`, `LEGAL_CHANGE_SUMMARY`, `DATA_CONTROLLER` with `[Pendiente]` fields, `consentPayload()`), `lib/privacy-api.ts` and `components/privacy/`. Every registration sends `consentPayload()` after `ConsentCheckboxes` (unchecked by default); Google accounts accept in `/complete-profile` (`acceptConsents()` before the profile PATCH). Any 403 `CONSENT_REQUIRED` makes the helpers dispatch `CONSENT_REQUIRED_EVENT`; `ConsentGate` (root layout) opens when `user.pending_consents` is not empty (not on `/legal/*`, `/account-suspended`, `/complete-profile`, `/google-callback`) and reloads the page after accepting if requests were rejected. `/profile` has `PrivacySettings` (`#privacidad`: consents, `downloadMyData` via fetch+Blob for the 429, `DeleteAccountDialog`). To publish a new text, change `lib/legal.ts`, the `/legal/*` page and the backend setting together. `DELETE` with a body goes through `deleteAuthRequestWithBody`.
- **Shared establishment management:** `components/establishment-management/` (`ProfileEditor`, `ProductsManager`, `CombosManager`, `GalleryManager`, `SchedulesEditor`) take an `api` from `lib/management-api.ts`: `restaurantManagementApi` (the `/restaurant/*` pages are one-line wrappers) or `adminManagementApi(id)` (`/admin/establishments/{id}/*`, with `setReason()` for profile edits). Add new panel features there, not in the page files; `uploadImage`/`ImageUploadField` take the upload-URL factory.
- **Suspended accounts:** any 403 `ACCOUNT_SUSPENDED` makes the request helpers dispatch `ACCOUNT_SUSPENDED_EVENT`; `AuthProvider` stores `suspended: { reason }` and redirects to `/account-suspended` (except `/legal/*`). Guards must not redirect to `/login` while `suspended` is set.
- **Reports:** `lib/reports-api.ts` + `components/reviews/ReportDialog.tsx` (`ReportButton` hides itself for admins and for the user's own content, and sends visitors to login). Used on reviews, establishment replies, the detail page and the restaurant reviews panel. `/legal/community-guidelines` is the target of every "Ver normas" link.
- **Shared helpers:** `lib/datetime.ts` (America/Bogota formatting, `timeAgo`, ISO with `-05:00`, month ranges, Google Calendar link), `lib/geo.ts` (distance, bounds, "Cómo llegar" links), `hooks/useGeolocation.ts` (asks for location only on a user gesture unless already granted), `components/common/RequireRole.tsx` (client role guard), `components/ui/EmptyState.tsx` and `components/ui/LoadMoreButton.tsx`.
- **Session context:** `components/providers/AuthProvider.tsx` (mounted in the root layout) fetches `/users/me` once and exposes `useAuth()` → `{ user, isLoading, refresh, clear }`. The `Navbar`, the admin layout and the restaurant layout read the role from it instead of calling the API themselves. If there is no session it re-fetches when the pathname changes (so login/register/Google callback are picked up); call `refresh()` after editing the profile and `clear()` on logout (`LogoutButton` does).
- `fase2-mapa-resenas-planes-frontend.md` is the phase 2 plan (map, reviews, moderation, notifications, plans, favorites, privacy), phases F0–F10 paired with the backend's B0–B10; its checkboxes record progress. Do not implement its section 15 ("Por planificar") without approval.
- `restaurant-account-frontend.md` at the root is the plan these areas were built from. Its tasks are checked off; its endpoint list predates the live backend OpenAPI (`http://127.0.0.1:8000/docs`), so trust the OpenAPI.
- `proxy.ts` (Next 16 name, not `middleware.ts`) guards `/admin`, `/restaurant`, `/profile`, `/notifications`, `/plans` and `/favorites` by checking only that the session cookie exists. Real role and status checks happen in the layouts against the API.

**Auth lives on cookies, not tokens.** The backend sets HttpOnly cookies. The frontend never reads or stores the session token; every request uses `credentials: "include"`. `lib/auth-api.ts` holds the central `AUTH_ENDPOINTS` map and the `get/post/put/patch/deleteAuthRequest` helpers, which throw `ApiError` with the backend's `detail`/`message` as the text (`apiErrorCode(error)` reads `{"code"}`, e.g. `CSRF_FAILED`). `lib/api.ts` only exports `API_URL` and the `Page<T>` type (`{ items, total, skip, limit }`). Send every write (POST/PUT/PATCH/DELETE) through these helpers so it carries the CSRF token; only the `GET /auth/google` in `LoginForm.tsx` and `GET /auth/csrf` in `lib/csrf.ts` call `fetch` directly.

**CSRF token.** The backend rejects POST/PUT/PATCH/DELETE without `X-CSRF-Token` (403 `code: "CSRF_FAILED"`). `lib/csrf.ts` keeps the token in memory only (never storage or cookies). Session-creating calls store it from `csrf_token` in the response: `loginUser`, `registerUser`, `exchangeGoogleCode` (in `auth-api.ts`) and `registerRestaurant` (in `restaurant-api.ts`), all through `rememberSessionCsrf`. `AuthProvider` calls `GET /auth/csrf` when it finds a session and there is no token yet (page reload). The write helpers add the header and, on `CSRF_FAILED`, refresh the token and retry once. `logoutUser` and `AuthProvider.clear()` drop it. The R2 upload in `lib/uploads.ts` (direct `XMLHttpRequest` to the bucket) must not carry it.

**Post-auth routing:** `resolvePostAuthRoute` in `lib/auth-api.ts` picks the destination after login (admin → dashboard; restaurant → dashboard if `APPROVED`, else `/restaurant/status`; user → `/complete-profile` or `/`, honoring a safe `?redirect=`). The register form and `google-callback` still use the older `registration_complete` check.

**Google OAuth round-trip:** `LoginForm` GETs `/auth/google` and redirects to the returned `authorization_url`. The backend returns the user to `/google-callback?code=…`. That page strips the code from the URL, then POSTs it to `/auth/google/exchange`, which sets the cookie. Its effect uses a `useRef` guard because of StrictMode double-invocation.

**Phone verification gate:** `complete-profile` loads `/users/me` on mount. A user whose profile already has `phone_verified`, a `nickname`, and `status === "ACTIVE"` is sent to `/`. The rest fill in the form, verify the phone via `/auth/phone/send-code` and `/auth/phone/verify`, and then save with a PATCH to `/users/me` (`nickname`, `phone_number` as `+57…`, `picture`). Route protection is client-side `useEffect` redirects; there is no `middleware.ts`.

**Cross-page state:** `RegisterForm` stores the typed phone in `sessionStorage["registrationPhone"]`, and `complete-profile` reads it to prefill. It is per-tab and does not survive a new session.

**Form convention:** each form is split into `X.ts` (a `useXForm()` hook with state, validation, and submit logic) and `X.tsx` (JSX). Import the hook with the `.ts` extension, for example `from "./LoginForm.ts"`; `allowImportingTsExtensions` is enabled for this. Validation regexes are duplicated across `LoginForm.ts`, `RegisterForm.ts`, and `CompleteProfileForm.tsx`. The phone rule is 10 digits starting with `3` (Colombian mobile, prefixed `+57`).

**Service worker:** `public/sw.js` is registered from the root layout by `components/ServiceWorkerRegistration.tsx`. It caches `/` and serves same-origin GETs cache-first, so stale responses are possible when debugging. It references `/icons/icon-192.png`, which is not in `public/`.

**Known gaps in the current code:**
- Profile pictures are set from `URL.createObjectURL(file)`, a local `blob:` URL that is not uploaded. It will not persist across sessions.
- The session cookie is `access_token` (checked in the backend settings). `proxy.ts` relies on that name.
- Restaurant signup uploads logo and banner after the register call, because the cookie exists by then and `upload-url` requires a session. It then saves them with `PATCH /restaurant/profile`. The backend allows that PATCH for `PENDING` accounts only when the body contains image fields. Upload folders are an enum (`establishments`, `menu`, `products`) and `file_extension` includes the dot.
- The restaurant panel, admin console, and public pages were verified only by type-check, lint, production build, and route-level redirects. No end-to-end run with real accounts has been done. The CSRF helpers and the notifications API layer were verified against the live backend from Node, not in a browser.
